# 客户端网络边界和新电脑验收

## 与 china-proxy 的分工

实际网络操作前发现并完整读取已安装的 [china-proxy](../../china-proxy/SKILL.md)，再按其路由读网络、Clash 或固定出口参考；优先读取机器已有网络单一事实源。不在本技能保存另一套代理规则，也不为了本次排障默认添加普通代理或切换 TUN。

只有桌面源码仓库中有该技能，并不表示当前宿主已加载它。缺少技能时说明限制并给出安装位置建议；不自动下载、改配置或绕过专用入口。

## 按客户端验证，不相互代替

| 客户端 | 必要核对 |
|---|---|
| 专用 Chrome | 独立 profile 的启动参数、实际入口、新请求链、OAuth loopback 绕过；不改系统默认浏览器 |
| 前台 CLI | 实际二进制/wrapper、有效配置、新进程 socket、请求 inbound/链、同入口的公网出口 |
| 后台 CLI 与 fork | supervisor/子进程实际环境与新请求；wrapper 退出后租约与守护仍否可用，重连是否改变路径 |
| Claude App | Dock 启动环境、登录/聊天/Code 或 Cowork 子进程分别测试；不会自动继承 CLI wrapper |
| 手机 | 当前配置与连接是否开启，实际落地与公网出口；Wi-Fi/移动网络切换需另外验证 |

用户要求多设备固定同一出口时，各设备独立测新请求和最终 IP；同名节点、同一订阅或连同一 Wi-Fi 都不能证明相同出口。城市库不同不等于 IP 变化；把公网 IP、地理标签、ASN、时区分别记录。未使用手机时不擅自配置或要求手机参与。

节点失效与整个 Clash 退出是不同故障。TUN 与 MATCH 非 DIRECT 只能证明运行时约束，不能保证整个客户端退出后不直连。显式专用入口、出口守护或系统层约束按实际作用范围验证，周期监测仍有发现窗口；不承诺零泄漏或全机 kill switch。

## 新电脑最小迁移流程

1. 发现 OS/架构、官方 CLI/App 支持、Clash 版本、当前订阅、配置生成来源和用户选择的认证模式；缺少落地/期望出口等重要选择才询问。
2. 安装官方程序和技能不复制旧电脑认证。按用户明确要求恢复非敏感 skills/hooks/settings，检查 hook/启动器里硬编码的旧路径和被停用脚本，不运行它们来猜配置。
3. 如用户要求网络配置，复用 `china-proxy` 的原生链式、国内白名单、DNS、备份与恢复流程。前置由用户可视化管理，固定落地不能自动更换。
4. `claude-safe` 等是自定义入口，不是官方内置功能。仅复制 Markdown/安装本技能不会获得保护；若需要迁移 guard/wrapper/专用 settings/OAuth helper，先列依赖和安装方案，得到授权后按新机器重新绑定路径、端口与期望值，不原样复制凭据。
5. 官方登录与 loopback 回调分别验证；先检查认证来源，不默认清空新机用户目录，不修改时区、浏览器指纹或默认浏览器。
6. 正常联网、配置恢复、节点失效、整个客户端退出、重启/订阅更新/新后台进程按当前授权验证。记录通过、失败和未测试；一次 IP 查询或成功登录不等于全部验收。

## 最小测试记录

私有记录包含日期/版本、客户端、启动入口、配置来源、被测请求类别、inbound/链、出口是否匹配、失败时处理、恢复结果和未测项。身份、实际地址和 org_id 不进公开仓库。

先保存工作再做任何故障注入或退出。仅测试方法、模拟输出或别的设备成功不能替代当前设备实测；清理后验证要同时检查配置保护是否仍在，不把“历史已清掉”当网络验收。
