# Claude 浏览器 / CLI 专用出口维护

## 架构与保护范围

本参考来自已遇到的故障和修复，不是自动安装脚本。存在现有实现时先读取配置与启动入口；没有实现时先提出方案，得到安装/修改授权后再做。不要从聊天历史复制凭据或公网 IP。

```text
独立 Chrome profile / 受保护的官方 CLI
  → 本机出口守护（示例 17890）
  → Clash 固定落地专用 listener（示例 17891）
  → 当前普通前置节点 → 用户的固定落地 → 官方服务
```

端口是案例，不是默认值。发现真实 `guard-config.json` / 有效 listener 后确认 listen/upstream/expected-IP/节点名称，避免端口冲突。普通 TUN 流量和主动使用专用入口的流量属于两个不同作用域。

守护只能连接约定的本机上游，不能在失败时自行连目标，也不能编辑 Clash、切换节点或自动接受探测到的新 IP。当前前置由 Clash 可视化页面管理，期望最终出口由用户确认。

## 出口守护行为

已有案例的参数是：后台通常每 20 秒复查，新连接距上次确认超过 10 秒先复查，确认最长有效 40 秒。实际维护以现有配置为准，不为“更安全”擅自改变频率。

- 两个独立探针中，任一取得有效但非期望 IP → 阻断。
- 两个都无法确认 → 阻断；一个确认期望 IP、另一个超时/TLS 失败时，现有实现可以允许，但需报告检测降级。
- 阻断同时拒绝新连接和关闭已有隧道；确认恢复后才允许。
- 校验上游 listener 的固定节点与有效前置关联，不能仅比较公网 IP。
- 只读本机状态页在阻断时仍可使用，不依赖海外联网；机器状态应包含服务标识、版本、健康度、期望 IP 和检测结果，不提供未授权修改接口。
- 这是周期检测，有发现窗口；长连接也存在窗口。不是逐包验证或系统防火墙，不能宣称“IP 变化瞬间零流量”。

如果没有系统层隔离，应用绕过入口的其他网络仍不受该守护保护。显式入口不监听时客户端应报错，不自动改用普通端口、TUN 或 DIRECT。

## CLI 启动与生命周期

- 保留官方安装器维护的二进制/symlink，以免更新覆盖 wrapper。受保护入口可独立命名，例如 `claude-safe`；如果用户需要简写，可用 shell function 调用它。
- 新 shell 的 `claude` function、旧 shell 的 `claude`、绝对路径二进制可能不相同。用 `type claude` 核实，不把同名命令当作已接管。
- CLI 启动/复用守护，使用 localhost HTTP 入口，并协调 HTTP/HTTPS/ALL_PROXY 的大小写版本。NO_PROXY 只包含必要 loopback，避免远程域名绕过。
- 需要隔离第三方 API 配置时只处理该子进程的冲突来源，保留用户正式认证。不能因代理排障删除所有认证；API 用户与 claude.ai OAuth 用户分开处理。
- 若用 `--settings` 提高网络配置优先级，说明是否允许用户追加/覆盖，避免项目配置悄悄改变路由。其余用户/项目权限与模型配置保留。
- 浏览器与 CLI 共用守护但可独立启动；用进程存活和有时效的租约判断 CLI 是否仍需守护。退出浏览器不能中断正在运行的 CLI，两者退出后可空闲超时停止。不要默认安装 LaunchAgent。
- 原生绝对路径可以仍读取代理设置，但不会因此自动获得启动检查、守护生命周期和专用登录浏览器，报告这条边界。

## 独立浏览器及 OAuth 回调

独立 profile 隔离登录数据，不伪装地区/设备、不默认改系统默认浏览器。读取实际 Chrome 可执行路径与 profile，使用受保护的代理入口；按需禁用 QUIC、非代理 WebRTC 等潜在绕行，并单独验证。

**已发生的回调故障**：Chrome `--proxy-bypass-list=<-loopback>` 会把本机回调也送到代理。官方 CLI 仍监听 `127.0.0.1:<临时端口>`，浏览器却显示 localhost 无法处理请求；这不是封号证据。

修正案例：

```text
--proxy-bypass-list=<-loopback>;localhost;127.0.0.1;[::1]
```

只放行字面 loopback 主机，不放行外部域名或整个局域网。若设置 `--host-resolver-rules=MAP * ~NOTFOUND`，同时排除真实本机回调主机。仍需本机 HTTP 服务测试；不能仅看 flag 文本。

排查顺序：

1. 不重放用户粘贴的 `callback?code=...&state=...`，也不输出浏览器包含令牌的完整 argv/URL。
2. 用 `lsof` / socket 检查 CLI 的临时 listener 是否存活，区分代理绕行、解析失败、进程退出和状态过期。
3. 备份并修正启动参数。完整退出该专用 Chrome 实例再重启；打开新窗口通常会复用旧进程，参数不会更新。先让用户保存工作，不退出其他 Chrome。
4. 用临时独立 profile、合成 `TEST_ONLY` 参数测试 localhost/127.0.0.1/IPv6 loopback；未测 IPv6 明确标记。再测一个外部合成域名仍到测试代理，不使用真实授权码。
5. 让用户取消失败认证，重新开始官方登录以取得新授权码。保持认证终端运行，等待成功，再读取脱敏状态；不要替用户输入凭据。

需要专用浏览器配合 CLI 时，只为 CLI 子进程设置平台支持的浏览器 helper，并确认客户端确实调用它。不修改 macOS 默认浏览器；桌面 OAuth deep link 与 CLI localhost callback 不混为一谈。

Chrome DevTools 不可用时说明连接状态，不声称查看过网页。若用户明确要求 DevTools，不静默换浏览器工具。端口/配置检查与临时合成测试不等于检查真实授权页面。

## 认证、模型与数据

`auth status` 只汇报是否登录、认证方式、服务提供方及必要套餐信息；不要求用户贴邮箱、orgId、OAuth URL。认证成功只证明登录，模型可用性须另测。

模型选择先核对官方模型 ID、客户端最低版本、套餐权限和现有配置。升级通过受保护入口执行，观察下载，保持官方更新路径；只为当前选择设置 `model`，不为模型切换改 API 地址或代理。最小验证禁用工具/自定义行为，核对结果中的实际模型 ID，不以模型自称为证据。旧会话与新默认值分开说明。

不要因登录报错直接删除 `~/.claude`、会话、组织文件或钥匙串。确有清理请求时先确认精确目标、保留范围和恢复能力，不把历史一次授权变成以后自动清空的规则。

## 桌面 App 和账号边界

- Claude App 从 Dock 启动，不执行 shell function，也不会自动继承独立 Chrome profile 或 CLI wrapper。
- TUN 可以接管一些 App 请求，但登录、聊天、Code/Cowork 子进程都需实际核对。未测前不声明它固定出口或 fail-closed。
- “节点断开”与“整个 Clash 退出”分开测。仅 TUN/域名规则不能承诺客户端退出后无直连；需要系统层约束时先说明方案及影响，另获授权。
- 官方桌面端不是因为安装本身就必封。固定 IP、时区、浏览器语言和任何检测结果都不是账号免封保证；使用资格按最新地区与服务条款核对，不用代理或指纹伪装替代资格。

## 恢复与测试记录

按层保留前一份配置：Clash 源扩展/可视化选择、守护代码和配置、浏览器参数、CLI 设置、shell function。恢复只覆盖本次修改，避免覆盖此后的用户新增设置；确认路径后再停止对应守护，不按广泛进程名批量 kill。

维护时记录哪些实测、哪些模拟、哪些未测。已观察到的合成测试包括不同出口阻断、探针部分失败、确认过期、已有隧道关闭、状态页可用、大响应完整转发、CLI 租约和回调绕过；它们不能替代桌面 App、IPv6、真实节点故障与整客户端退出的验证。
