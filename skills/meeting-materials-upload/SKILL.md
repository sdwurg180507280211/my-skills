# 会议资料网站上传

把本地资料、会议记录、存储对象、文件登记和实时审核状态分别记账。默认采用已验证的混合路线：**页面同源 Aura 调用 → 本机预签名 PUT 直传 → 页面登记 → 全量接口对账**。平台接口以当次抓到的真实请求为准，历史参数用于识别接口，不代替当前会话和业务规则。

## 读取路线

- 执行建会、上传或续传前，读 [references/aura-upload.md](references/aura-upload.md)：接口、编码、类别、三步上传与异常恢复。
- 执行替换、删除、重建或状态查询前，再读 [references/reconciliation.md](references/reconciliation.md)：目标匹配、状态边界、删除白名单与验收。
- 本地清单和实时列表的确定性检查使用 [scripts/check_upload.py](scripts/check_upload.py)。它只读文件、输出 JSON，不联网、不删文件、不上传。
- 使用网站时先读宿主可用的 `chrome-devtools` Skill；读取本机全局网络规则，默认采用既有系统路由。缺少浏览器工具或登录会话时如实说明当前限制，不把技能安装视为已经连接浏览器。

## 先明确本次范围

1. 从会话提取用户给出的项目页面、资料版本、会议范围、命名和类别规则、操作授权。用户已经确认的选择直接沿用。
2. “看一下有没有驳回”“核对数量”仅做只读查询；“上传/继续上传”允许范围内建会与传资料；删除会议需要明确的删除范围授权。上传本身不自动授权删整场会议、提交审批或修改审批完成会议。
3. 换项目同步核对项目 ID、页面路径、名称规则和资料根目录。项目 ID 必须从当前页面取得；旧脚本里的项目常量不能继承。程序输入不设置真实项目的默认值。
4. 当前项目实时列表和本地目标集合分别统计。项目顶部“完成/计划场次”是业务汇总，不能拿来替代列表总数或上传进度。

## 本地预检与权威清单

先定位真正的会议目录层，处理解压后的同名嵌套目录；限定用户指定的最新版，排除备份版本、隐藏目录、锁文件和工作产物。

单人资料的历史映射如下；文件名中的 `/` 在本地可能表现为子目录，扫描时使用相对路径，不只取 basename：

| 类别代码 | 本地常见相对路径 | 网站完整类别 |
|---|---|---|
| A | `最终会议议程-海报.jpg` | 最终会议议程 |
| B | `参会者签到表/线上会议参会报告-参会明细.xlsx` | 参会者签到表/线上会议参会报告 |
| C | `付费服务提供者照片/截屏-课前.jpg` | 付费服务提供者照片/截屏（例如：主席/讲者/讨论嘉宾等） |
| D | `会场照片/截屏-课中.jpg` | 会场照片/截屏 |

多人会议通常有海报、观看报告和按讲者分类的课前/课中/课后截图。同一张图进入几个类别、会场栏取一张还是多张，以当前用户规则或已核实的参考会议为准；不能把历史的每场 20 条或 12 条当作固定政策。

确认文件存在、非空、可读取，并记录扩展名、实际格式和哈希。扩展名与编码不一致单独记录；采用当前页面已经验证的 Content-Type 策略，签名和 PUT 必须完全一致，不静默改名或转码。

内容审核复用当前 `meeting-reimbursement-audit` Skill 或用户已验收的结果，不复活旧的正脸、完整五官、真人视频等已撤销规则，不自行扩大审核范围。`REVIEW`、读取失败和已确认的问题不得悄悄写成“通过”；用户明确接受某项例外时记录其范围。保留原图，不生成或修补会议证据。

每场清单记录名称、日期、相对文件路径、类别、哈希、审核结论；建立实时会议对应关系后加入项目 ID、会议 ID 和编号。后续 objectKey、预签名、PUT、登记和核验都从同一份清单生成，禁止手抄长 URL 或复制旧批次的数据。

## 系统对账与建会

开工先获取当前项目全量列表，按目标集合匹配。名称有无项目前缀、同日多场和重复姓名均需处理；不按页面顺序或只按姓名匹配。最终写操作以已核实的 `recordId` 为键。

- 已存在且附件证据完整：跳过；需要替换时进入指定文件的替换流程。
- 已存在但缺附件：查清实际缺口，复用会议 ID 补传，不重新建会。
- 目标缺失：先排除命名差异和查询不完整，再按用户授权创建。
- 匹配有歧义：单列待处理，继续处理能够明确对应的场次。

按日期时间排序串行建会；服务端按创建时序分配编号，不能承诺连续编号或恢复旧编号。每条取得新 ID 后立即写入任务台账，并用实时列表核对名称、日期和所属项目。不要建“格式测试”垃圾记录；需要试点时选本次真实、授权的目标。

## 批量执行与续传

1. 先用一场真实目标跑完整链路，核对类别、文件卡片和实际文件可打开。
2. 按小批运行。历史起点：建会每次约 10–20 场、预签名每次最多 10 个文件、登记每场一次、任务每批约 5–10 场。这是旧工具超时下的保守起点，按实际工具限制调整。
3. objectKey 去掉文件名的最后一个扩展名后，拼接唯一时间戳和**当前会议 ID**；不复制旧 ID、旧时间戳或旧批次参数。
4. 将预签名结果程序化保存并逐个校验 URL 的完整对象路径；再按清单的 Content-Type 直传。逐文件记录实际 HTTP 状态、objectKey 和哈希，失败不进入登记。
5. 每场只登记本场已经成功传输的文件；类别字符串精确匹配，顶层 recordId、每项关联 ID、objectKey 和批次范围必须一致。
6. 每批重拉系统列表，核对四栏、预期卡片数和对象证据。多人栏目有一个文件就可能亮勾，不能只看四个勾判断数量齐全。

续传由剩余集合驱动，不由“第几批”或旧进度数字驱动。工具超时、浏览器重启或页面刷新后先查询实际结果：超时的页面脚本可能仍在执行，盲目重发会重复建会或登记。重找页面并恢复助手后，补已证明缺失的步骤。会话是否有效要实时验证，不能保证重启后 token 永远可用。

预签名常见有效期为 3600 秒；中断后检查新鲜度。过期时为原 objectKey 重新签名；未知结果的 PUT 先查传输日志或对象，不把所有 403 都当作过期。

## 本地检查入口

`check_upload.py batch` 接收一个规范化批次对象，包含 `batchId`、`projectId`、`recordIds` 和 `files`；每文件包含 `batchId`、`projectId`、`recordId`、`path`、`name`、`category`、`contentType`、`objectKey`、`timestampMs`、`sha256`。schema 及示例见上传参考文件。`putUrl` 可选，提供时检查精确对象路径；真实 URL 只留当次私有任务目录。

```bash
python3 -B <skill-dir>/scripts/check_upload.py batch <任务目录>/batch.json
python3 -B <skill-dir>/scripts/check_upload.py verify <任务目录>/targets.json <任务目录>/live-list.json
```

`verify` 的目标输入是会议 ID 数组；列表支持已抓到的 Aura 包装或 `{state, rows}` 格式，拒绝失败响应。它显示目标范围和页面总量的不同统计。四栏齐全只叫“登记栏位齐全”，不能单独称为最终上传验收。

## 验收与交付

最终逐条闭合：目标总数 = 已完成 + 已确认跳过 + 失败/待处理；失败/待处理为零时才报告全部完成。按用户需要给出新增哪些、补传哪些、替换哪些、未处理哪些，并链接本地台账。

验收同时检查：本地版本和哈希、正确新会议 ID、PUT 成功证据、完整类别、真实卡片数量/关联、实际对象可访问。四个勾只证明相应栏目有登记记录，空 key 也曾亮勾；文件内容正确性由源资料验收负责。

清单、创建结果、传输日志、登记结果、系统快照和最终摘要保存在任务目录；MCP 只允许临时路径时立即转存。共享文档和公开 Skill 不保留 Cookie、token、签名 URL、真实项目 ID/链接、参会名单、图片或本机绝对路径。认证尽量只在浏览器内存流转；必要的私有运行文件限制访问且排除版本控制。

## 离线测试

```bash
python3 -B -m unittest discover -s <skill-dir>/tests -v
```

测试使用合成文件，覆盖精确 URL 配对、类别全称、跨项目/跨批错绑、哈希变化、四栏和目标集合统计、失败响应拒绝。不调用真实网站；测试通过不代表真实项目已上传。
